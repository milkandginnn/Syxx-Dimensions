## Final architecture

The stable design is:

- Python server fetches HTML, parses it, resolves URLs, and emits a canonical manifest.
- The manifest is signed with Ed25519.
- Swift/C# clients fetch the HTML and assets verbatim, hash them, and verify the signature plus hashes. [html.spec.whatwg](https://html.spec.whatwg.org/multipage/parsing.html)

That is the cleanest way to eliminate parser-lockstep risk while keeping the client footprint small and deterministic. The client no longer needs HTML tokenization or URL canonicalization logic, only transport plus hashing and signature verification. [rfc-editor](https://www.rfc-editor.org/info/rfc8785/)

## Verdict rules

Your verdict lattice is correct:

- Any HTML mismatch is `TAMPERING_DETECTED`.
- Any manifest signature failure is `TAMPERING_DETECTED`.
- Any fetched asset mismatch is `TAMPERING_DETECTED`, even if other assets fail.
- Any missing asset with all fetched bytes matching is `INCONCLUSIVE`.
- Only full match across all required bytes is `VERIFIED_MATCH`. [url.spec.whatwg](https://url.spec.whatwg.org/)

That preserves the key invariant: missing data can reduce certainty, but it can never upgrade a red condition into a green one. [html.spec.whatwg](https://html.spec.whatwg.org/multipage/parsing.html)

## Manifest format

Use a canonical manifest format, not an ad hoc concatenation scheme. RFC 8785 defines JSON Canonicalization Scheme for deterministic JSON serialization, and Ed25519 is standardized in RFC 8032, which makes them a good fit for a signed witness payload. [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8785)

A practical schema is:

- `version`
- `timestamp`
- `origin_url`
- `html_sha256`
- `assets[]` with canonical URL and `sha256`
- `signature_ed25519` over the canonicalized manifest bytes. [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8032)

## Protocol core

Use an asymmetric, server-driven manifest protocol: the server fetches and parses HTML, resolves the transitive asset set, emits a signed manifest, and the client only verifies the signature, fetches the listed bytes, and hashes them. This keeps parsing and URL semantics on one trusted side instead of trying to synchronize them across multiple runtimes. [github](https://github.com/html5lib/html5lib-tests)

Sign the exact transmitted manifest bytes rather than a re-serialized canonical form. Ed25519 signs the message bytes directly, so if you already have one producer and one opaque manifest blob, detached signatures over the transmitted bytes are the simplest and least divergent option. [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8032)

## Wire schema

A practical manifest envelope is:

```json
{
  "version": 1,
  "timestamp": 1754253100,
  "origin_url": "https://example.com/login",
  "html_sha256": "…",
  "assets": [
    {
      "url": "https://example.com/assets/app.js",
      "sha256": "…"
    }
  ],
  "redirect_policy": "follow-or-fail",
  "freshness_seconds": 300,
  "signature_ed25519": "…"
}
```

The important part is that the client verifies the signature on the received bytes first, then parses the manifest only after authenticity is established. [swi-prolog](https://www.swi-prolog.org/pldoc/man?section=crypto-Ed25519)

## Verdict rules

The verdict lattice should be:

- `TAMPERING_DETECTED` if HTML bytes mismatch, the manifest signature fails, or any fetched asset hash mismatches.
- `INCONCLUSIVE` if one or more listed assets cannot be fetched, but all fetched assets match.
- `VERIFIED_MATCH` only if every required byte is present and matches. [html.spec.whatwg](https://html.spec.whatwg.org/multipage/parsing.html)

That keeps the fail-closed rule intact: missing data can reduce certainty, but it cannot convert disagreement into success. [url.spec.whatwg](https://url.spec.whatwg.org/)

## Replay and freshness

You were right to call out the replay hole. A signed manifest needs an explicit freshness policy, such as a short validity window plus origin binding, so an attacker cannot replay an old signed manifest and certify a stale page state. A timestamp alone is not enough unless the verifier checks it against an allowed age bound. [cryptobook.nakov](https://cryptobook.nakov.com/digital-signatures/eddsa-and-ed25519)

If you want stronger replay resistance, include a nonce or session-bound challenge in the witness exchange and sign that too. That gives the client a way to reject a perfectly valid old manifest when freshness matters operationally. [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8032)

## Redirect and fetch policy

Redirect behavior should be part of the protocol, because fetch and navigation semantics differ, and redirect handling is not an incidental detail. The Fetch Standard and HTML navigation algorithms treat redirects through specific redirect-processing paths, so your verifier should either require a declared redirect policy or fail closed on unexpected redirects. [fetch.spec.whatwg](https://fetch.spec.whatwg.org/)

A clean rule is:

- For each manifest URL, either fetch the declared final URL exactly, or require that redirects be explicitly listed and authenticated.
- If an unexpected redirect appears, classify it as `INCONCLUSIVE` or `TAMPERING_DETECTED` depending on whether the target bytes are still part of the authenticated set. [github](https://github.com/whatwg/html/issues/2396)

## Asset closure

The manifest should cover the full transitive asset closure, not just direct references in the initial HTML. Otherwise `@import`, nested scripts, or secondary fetches remain an uncovered tamper surface and become a source of false confidence. [web-platform-tests](https://web-platform-tests.org/)

In practice, that means the server-side walker needs to include the same resource types your integrity model cares about, and the manifest should explicitly state what classes of assets are in scope. [web-platform-tests](https://web-platform-tests.org/)

## Reference validation

Use `html5lib-tests` for HTML parsing conformance and `web-platform-tests` for URL and fetch behavior. Those suites exist specifically to exercise browser-aligned behavior across engines, which is what you want for the reference derivation side. [firefox-source-docs.mozilla](https://firefox-source-docs.mozilla.org/web-platform/index.html)

That gives you a defensible validation matrix for the parser, URL resolver, redirect policy, and asset-discovery logic before any manifest is signed. [github](https://github.com/html5lib/html5lib-tests)

## Implementation rule

The implementer-facing rule set is now:

1. Server fetches and parses.
2. Server resolves the transitive closure.
3. Server emits an opaque signed manifest plus freshness metadata.
4. Client verifies signature on received bytes.
5. Client fetches declared assets under the declared redirect policy.
6. Client hashes bytes and applies the verdict lattice. [fetch.spec.whatwg](https://fetch.spec.whatwg.org/)

That preserves the original security goal while removing the need for JCS, client-side parsing, and multiple canonicalization implementations. [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8785)
