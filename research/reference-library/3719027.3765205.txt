Abstract
macOS delegates many high-privilege operations to dedicated PIDdomain services, which applications can register and communicate
with through inter-process communication (IPC). This architecture
improves userland stability and security but also introduces attractive attack surfaces for adversaries. In this paper, we systematically
analyze PID-domain services and uncover an overlooked attack
vector: PID-domain services that are restricted to an Application
Sandbox identical to the calling application can still be exploited
due to subtle entitlement differences.
To fully understand this attack surface, we reverse-engineered
the implementation of the entitlement mechanism for the Application Sandbox in macOS. Based on these insights, we designed
an entitlement-guided taint analysis framework to automatically
detect vulnerable PID-domain services within this attack surface.
Using our detection tool, we identified 19 confirmed zero-day vulnerabilities in the latest macOS 15.2, with 7 assigned CVE identifiers.

Introduction

Apple’s macOS is widely recognized as one of the most secure commercial operating systems. Apple’s relentless emphasis on user privacy and data protection is evident through its sophisticated multilayered defense strategy, integrating robust security mechanisms
across both software and hardware components. At the hardware
level, technologies such as the Secure Enclave coprocessor [8], hardware root of trust, and secure boot processes provide foundational
assurances, ensuring the integrity and authenticity of software
components right from system startup. Complementing these hardware protections, macOS incorporates advanced software-based
defenses, including System Integrity Protection (SIP), Gatekeeper,
Sandboxing, Transparency, Consent, and Control (TCC), and the
entitlement-based permission system, systematically limiting privileges and enforcing strict runtime constraints.
A crucial element of macOS’s software security architecture is
its sandboxing and inter-process communication (IPC) mechanism,
explicitly designed to enforce the principle of least privilege by isolating applications and restricting their access to system resources.
Third-party applications are constrained within an application sandbox environment. To interact beyond their sandbox boundaries
(e.g., invoking system services or helper utilities), macOS provides
a robust IPC mechanism known as XPC. XPC allows applications
to delegate specific tasks to helper services or system daemons, enhancing stability and modularity without compromising security.
Depending on their sensitivity and intended design, macOS services operate within three distinct domains: the System domain,
User domain, and PID domain. System-wide daemons and widelyaccessible services typically reside within the System or User domains, subject to global access restrictions enforced by specific permission checks. Conversely, each sandboxed application manages
its own dedicated PID domain—a private namespace isolating its
XPC services from other applications. Services within PID domains

escape the Application sandbox. The only two known attacks targeting PID-domain services typically involve privilege escalation

variations can inadvertently become exploitable by malicious applications. We term this newly identified attack vector "Chekhov’s
Gun", drawing from the literary principle suggesting that any "gun"
presented in a narrative is eventually fired. The analogy illustrates
how an extra capability or entitlement included in a seemingly benign component (the PID-domain service well restricted in the Application Sandbox or the "gun on the wall") may eventually be leveraged maliciously when the component falls under an attacker’s
control. To the best of our knowledge, this paper represents the
first systematic exploration into how a malicious sandboxed application can exploit PID-domain services that also operate within
Application Sandbox to break macOS’s protection.

are summarized as:
● We conduct the first systematic analysis of the PID-domain service attack surface on macOS, revealing a previously unexplored
vector termed the Chekhov’s Gun attack, where PID-domain services restricted by Application Sandboxs remain vulnerable.
● We demystify how entitlement-check mechanisms are implemented within the macOS kernel and clarify their interplay with
the sandbox security model.
● We design and implement a semiautomated entitlement-guided
taint analysis framework1 specifically tailored to this newly identified attack surface. Our framework systematically discovers exploitable paths by tracing data flow from externally accessible
APIs to sensitive operations. We evaluated our tool on macOS 15.2,
demonstrating its practicality by effectively discovering 19 previously unknown zero-day vulnerabilities.
Responsible disclosure. We disclosed all vulnerabilities we identified and the Chekhov’s Gun attack to Apple via the Apple Security
Research platform in December 2024. Apple engineers have confirmed 19 vulnerabilities and assigned CVEs (CVE-2025-24249, CVE2025-43273, CVE-2025-43365, CVE-2025-30448, CVE-2025-24205,
CVE-2025-24207, CVE-2025-24248). As of the time of writing, these
CVEs have been patched in macOS 15.6.1. All affected PID domain
services have had entitlement checks added to reject unauthorized
access and removed some exported APIs. The remaining vulnerabilities are planned to be fixed in the Fall of 2025.

2 Background
2.1 Layered User-space Protection in macOS
Apple enforces multiple layers of user-space protections in macOS
to limit the actions of potentially malicious or compromised applications. At the hardware level, modern Apple devices rely on many
hardware features, such as the Secure Enclave, Pointer Authentication (PA) [12], and Page Protection Layer (PPL) [6], which have
significantly raised the bar for kernel exploitation. At the software
level, System Integrity Protection (SIP) [7] further reduces the risk
of unauthorized code execution. Building on these low-level safeguards, macOS employs additional measures in user space, including sandboxing, TCC (Transparency, Consent, and Control), and
entitlements, to confine application behavior and mediate access to
sensitive resources.

A Tailored Static Detection Framework. To systematically uncover vulnerabilities within the identified PID-domain attack surface, we developed a static analysis framework capable of automated vulnerability discovery and evaluation. Our approach begins by exhaustively scanning the macOS filesystem to identify
connectable XPC services. We then reverse-engineer these binaries, examining their entitlement-check mechanisms to filter out
services that are realistically connectable, and extract publicly exported APIs to define source points. Next, we systematically map
undocumented entitlements to sensitive operations (sink points).

Sandboxing Protection. A core component of Apple’s user-space
defense is the App Sandbox, a mandatory access control (MAC)
framework inherited from iOS. As Deaconescu et al. and others
have shown, the sandbox confines an application to a limited set
of operations, preventing unauthorized access to the file system,
network, or other system resources. This mechanism applies to all

2.3

PID-domain XPC Services

Depending on the specific operation requirements, PID-domain services in macOS can be executed within a Service Sandbox [25] or an
Application Sandbox [1]. Their difference is summarized in Table 1.
Service Sandboxes are explicitly activated through dedicated
sandbox initialization API calls, allowing developers to specify customized sandbox profiles tailored to the operational needs of individual system daemons or services. These profiles typically grant
services varying privilege levels, including elevated access at root
or system levels essential for performing specific tasks. File system
interactions are precisely controlled by explicitly specified paths
within the sandbox profiles, and network access or inter-process
communications are regulated through detailed rules. Due to their
relatively permissive profiles, service sandboxes are commonly
adopted by system daemons and processes, which grant broader
access to sensitive system resources. Unlike application-generated
outputs, files created by service processes do not undergo automatic quarantine; instead, developers must explicitly implement
tagging if quarantine measures are needed, highlighting the importance of careful configuration to safeguard against vulnerabilities.
In contrast, Application Sandboxes automatically apply security
controls upon application launch, enforcing a generic sandbox profile suitable for typical application behaviors. This built-in profile
restricts applications strictly to user-level privileges, effectively preventing unauthorized access to critical system resources. File operations within Application Sandboxes are containerized, isolating application data and significantly mitigating potential risks from compromised software. Additionally, network interactions and interprocess communications are tightly managed through entitlementbased permissions mediated by trusted broker services, further limiting the exposure surface for security breaches. Outputs generated
by applications within these sandboxes are also quarantined.

TCC Protection. Complementing the sandbox and entitlement
protection, Apple’s Transparency, Consent, and Control (TCC) enforces user authorization for accessing sensitive data like photos,
contacts, and location. It intercepts access attempts and prompts
users for consent, storing preferences in System Settings. To support
essential functionality, some Apple system apps are granted private
entitlements (e.g., com.apple.private.tcc.allow) that let them
bypass prompts for trusted operations—such as Calendar accessing
address book entries. These entitlements are restricted from thirdparty use, preserving TCC’s role in confining untrusted apps while
enabling trusted system components to operate seamlessly.

Interprocess Communication (IPC)

When operating cohesively, macOS sandboxing mechanisms provide robust isolation, significantly limiting the actions of potentially
compromised apps. In reality, however, macOS still needs to facilitate controlled inter-process communication (IPC) for legitimate
tasks such as accessing iCloud, printing, or handling Apple Events.
These IPC operations typically rely on Mach messages and XPC
services, where a privileged or less-restricted service performs specific actions on behalf of a sandboxed application. At the heart of
IPC is launchd (PID 1), macOS’s central service manager, responsible for registering, launching, and managing Mach-based services,
including XPC services, within defined namespaces—System, User,
and PID domains. While sandbox policies restrict an application’s
communication to whitelisted services unless explicitly entitled

3.1

Threat Model

Our threat model assumes that the attacker is a sandboxed application. The application is confined to its own Application Sandbox
and can only read or write files within its designated container. It
is explicitly restricted from accessing other system resources or
user data beyond the sandbox boundary. Furthermore, the attacker
cannot self-declare any restricted public or private entitlements,
as these require explicit approval through Apple’s notarization or
code-signing process. This threat model reflects the realistic constraints faced by third-party applications in the macOS ecosystem
and explicitly excludes any form of privileged code execution or
kernel-level access.
Despite these stringent sandbox restrictions, we show that a
malicious sandboxed application can still mount powerful attacks
by abusing PID-domain services. In particular, we show how such
an app can exploit PID-domain services to carry out operations that
are explicitly disallowed by the Application Sandbox policy, such as
TCC and SIP, thereby violating core security guarantees enforced
by macOS. This attack can succeed when all three of the following
conditions are met: (1) the application is able to invoke a PID domain
service that carries a sensitive entitlement that the application itself
is not permitted to have, (2) the PID domain service exposes an
API whose behavior effectively grants the sensitive entitlement’s
capabilities, and (3) the application has a valid path or control over
one or more parameters that reach the sink.

function properly. Chekhov’s Gun attack exploits and reveals the
subtle differences in entitlement configurations between attackercontrolled applications and these PID-domain services.

beyond the sandbox is further gated by SIP, TCC, and additional entitlement checks, effectively narrowing the attack surface. Notably,

architecture. The system fundamentally relies on entitlements to

Importantly, because certain PID-domain services must perform
operations that exceed the capabilities permitted by a standard
Application Sandbox, Apple grants them specific entitlements to
support their privileged functionality. These entitlements are carefully curated to ensure the service can function while preserving
broader system security. However, this design also introduces a
subtle but critical asymmetry: the entitlements assigned to these
services differ in small but meaningful ways from those available
to ordinary sandboxed applications. Chekhov’s Gun attack exploits
these fine-grained entitlement differences to perform actions that
are normally prohibited by sandbox policies. In the following section, we demonstrate the vulnerabilities we discovered: even when

Exploiting the Vulnerability via Exported APIs. Our analysis identified a vulnerable API, startFileSharing, by tracing data
flows from its controllable input parameters. The first parameter,
a file path, is propagated through several function calls and ultimately reaches BRSharingCreateShareForItemAtURL at line 8.
This function uploads the specified file to an iCloud server and returns a publicly accessible URL, allowing arbitrary file downloads
from the victim’s iCloud storage without user authorization.
To identify this vulnerability, four conditions need to be met.
The first is a special capability, where we analyze the service’s
entitlements to determine what capabilities it possesses. The second
is identifying the exported APIs, which indicate which APIs are
callable. The third condition is pairing the special capability with
sensitive functions. This involves collecting the relevant sensitive
functions based on the special capability. The last condition is
the exploitable sensitive function, where the sensitive functions
collected earlier need to be influenced by controllable parameters
from the exported APIs in order to be exploited.
End-to-end Test. We conducted an end-to-end attack on our local machine to confirm the feasibility of exploiting SPIHelper.xpc.
One additional necessary step was registering the target PID-domain
service. This registration can be achieved through explicit registration APIs [24] or implicitly by loading Apple’s third-party libraries,
which automatically handle service registration during initialization. Once registered, our proof-of-concept successfully triggered
the vulnerability, enabling arbitrary read of iCloud files.

To demonstrate how the identified architectural components can be

This vulnerability allows attackers to arbitrarily read and download

A Static Analysis Framework for Detecting
Chekhov’s Gun Attack

To automatically assess the new attack surface identified by the
Chekhov’s Gun attack, we design a static analysis-based detection
framework to analyze PID domain services at scale. Our goal is
to identify which PID-domain services can be connected to, discover the APIs they export, and then determine whether any of

filtering functions based on sensitive operations. Because Apple’s

we correlate each service’s entitlements with its exposed functions,

the first parameter of the callback, and continue the taint analysis
from there. If the next function is an Objective-C function, I follow
the Objective-C calling convention, starting the taint analysis from
the third parameter onward. If the next function is a C function, we
perform the taint analysis starting from the first parameter, as is
typical for C functions. If taint successfully propagates across function boundaries and reaches a sink parameter, the path is considered valid. In this case, the source is deemed potentially exploitable.

6.2

Countermeasures

Apple’s mitigation. Apple’s mitigation against Chekhov’s Gun
relies on entitlement-based authentication: only requesters with
the correct entitlement can invoke the sensitive exported APIs of a
service. While this ensures that only properly signed and entitled
clients gain access, it also imposes a painstaking remediation process. Apple must first identify every app or service that legitimately
uses a given PID domain service, then re-sign or update each with
the new entitlement before pushing a patch. This mitigation strategy was chosen to preserve backward compatibility and to integrate smoothly with its existing code-signing infrastructure. However, it comes at the expense of a slow, service-by-service rollout
and a gap window in which unpatched services remain exposed.

Limitations

Although the proposed detection framework can identify the attack
surface at scale, our analysis also revealed several limitations.
Evolving Platform and Format Compatibility. Apple’s ongoing revisions to the Mach-O file format prevent our framework
from working seamlessly across versions, as it relies on the parsing of specific Objective-C segment structures to locate exported
APIs. Thus, each new version release therefore demands a quick
adaptation cycle: (1) reverse-engineer one representative binary
and record any shifted Objective-C metadata offsets; (2) update the
parser with those offsets; (3) rescan binaries to refresh the source
and sink lists for added or removed functions. Adding to this challenge, our analysis pipeline, including all data flow and taint tracking logic, depends on the intermediate representation of IDA Pro.
When Apple alters its compilation strategies, IDA Pro disassembly
can suffer from missing instructions or flawed control-flow reconstruction, which in turn degrades the fidelity of our taint analysis. Moreover, Swift also introduces significant complexity. Apple
has been gradually rewriting parts of its Objective-C codebase in
Swift. Compared to Objective-C, Swift introduces advanced language features such as generics and functional programming constructs, which pose major challenges for reverse engineering. While
IDA Pro has added partial support for Swift disassembly and decompilation, it remains imperfect. Swift’s language characteristics,
such as deep indirection, opaque runtime behaviors, and closureheavy patterns, continue to make data flow analysis difficult.

6.4

Confused-Deputy Attack Comparison

Traditional confused-deputy attacks hinge on an unprivileged caller
tricking a more privileged ‘deputy’ into performing sensitive actions on its behalf. On Android, for instance, a classic confuseddeputy / permission-re-delegation attacker [17, 48] first (i) locates
an exported component under a different UID that already holds the
desired Manifest permission—readily found by Epicc [38], (ii) asks
that component via Binder/Intent to invoke the protected API, and
(iii) succeeds because the framework checks only the callee’s UIDpermission pair. Static analyzers such as FlowDroid [10] or crossUID Binder monitors can detect this confused-deputy flow. In Web3,
Confusum Contractum [21] reveals a parallel pattern: By rewriting a
CALL / CALLCODE in a victim contract, the attacker causes the victim’s address to become msg.sender in a target contract that trusts
that address for privileged actions (e.g. token transfers). Here, no
UIDs exist, only address-based trust, so detection tools usually hunt
for controllable CALL sites or address mismatches on Ethereum.
By contrast, macOS breaks each of the classic confused-deputy
steps in a fundamentally different way. Its ‘deputy’ is a PID-domain
XPC service that shares the same UID and sandbox profile as the
caller. Its Mach/XPC endpoint is guarded by a private, code-signed
entitlement invisible to manifest-style scans; the decisive check
occurs later in kernel helpers (e.g., apfs_is_task_entitled()),
which drop all notion of the original caller’s identity. As a result, Android and Web3-centric detection methods, including Epicc, FlowDroid, Binder monitors, and Ethereum address analyses, cannot
work here. Chekhov’s Gun instead exploits this hidden, entitlementbased trust inside the IPC mechanism, requiring a new pipeline
of XPC-service enumeration, hidden-entitlement extraction, and
binary-level taint analysis.

Coverage Gaps and Need for Manual Oversight. Achieving
completeness in identifying sink functions remains inherently challenging, which is also a common and widely recognized problem
in bug discovery. Although we combine manual expertise with automated LLM-based methods, the intrinsic limitations of semiautomated analysis flow (such as context window constraints, imperfect semantic understanding, and potential hallucinations in LLMgenerated output) mean that our sink lists and entitlement-to-sink
mappings could not fully capture all possible cases. To accommodate these limitations, we design the sink list and the entitlementto-sink mapping as two distinct modular documents; each can be
corrected and extended over time. Moreover, we will release our
generated lists for future research.

It collects a source list, hand-crafts a small sink list, and enhances

enables us to generate a comprehensive entitlement-aligned sink
list with reasonable manual effort, tailored to detect the inconsistency and vulnerabilities caused by entitlement difference.

XPC-based Attacks in macOS

Kobold [15] employed black-box fuzzing to discover callable APIs
within services. During this process, it also constructed an entitlement mapping table by observing error messages when connection
attempts failed, thereby inferring which entitlements were required
to access specific services. Kobold then manually analyzed the accessible APIs to identify those related to sensitive or privacy-critical
operations. iService [46] also explored the confused deputy problem
in XPC services. It introduced an automated static analysis tool for
Objective-C, framing the confused deputy issue as a data-flow reachability problem. After automatically identifying accessible APIs in
each service, it defined a set of sensitive sink functions, and used
taint analysis to determine whether attacker-controlled input could
reach those sinks. However, they focused exclusively on system and
user domain services, overlooking PID domain services, which account for approximately 40% of all services, a major attack surface.
In the industry, several works demonstrated entitlement-based
attacks on sandboxed services. For example, Jin et al. exploited SIP
entitlements to bypass SIP via the domain service of the xpcroleaccounted system [36, 37], which runs inside a service sandbox. They
also disclosed the PID-domain attack surface, and demonstrated
entitlement-based attacks on PID domain services within the service sandbox using SIP- and TCC-related entitlements. However,
unlike system and user domain services, which generally reside in
the service sandbox, a significant portion of PID domain services
operate under the more restrictive application sandbox. Through
our reverse engineering of the entitlement mechanism, we found
that entitlements form a foundational layer of user-space security.
Entitlements grant specific capabilities to a service, and sandbox
enforcement yields to those entitlements. Therefore, entitlementbased attacks remain applicable to services inside the application
sandbox, a fact that has been overlooked. Moreover, prior industry efforts to identify entitlement-based attacks have relied heavily
on manual reverse engineering and have focused only on a small
subset of known entitlements related to SIP and TCC.

7 Related Work
7.1 Prior Work on macOS Userspace Protections
Prior research primarily focused on analyzing the sandbox mechanism. FG1 [19] pioneered the semantic analysis of sandbox profile rules and created a rule reference manual. Subsequent studies by Stefan et al. [40], Census Labs [13], Jonathan et al. [29], and
Karol et al. [35] systematically reverse-engineered macOS sandbox implementations from user space to kernel space. These works
demonstrated how Apple utilizes the MACF framework [34] to enforce system resource access control, with primary differences lying in the macOS versions analyzed. Modern sandbox implementations incorporate additional system call hooks to expand protection coverage. For other mechanisms, Keith et al. [26] and Stuart et
al. [11] detailed TCC’s operation through its TCC.db consent database, while Apple’s official documentation [5] specifies SIP’s ability
to protect system files from root-privileged modifications. Despite
this progress, the entitlement mechanism remains understudied
with limited explaination in Apple’s documentation [2].
Existing research only provides fragmented insights. For example, Stefan et al. [40] briefly noted kernel-level entitlement checks
during sandbox analysis but offered no systematic examination. Industry reports [25, 37, 43] revealed attacks abusing undocumented
entitlements to bypass SIP/TCC, yet failed to explain how attackers
discovered these capabilities and address the fundamental questions.
To answer the three questions, we dive into entitlement kernel implementation. Through kernel-level reverse engineering, we identify two critical entitlement enforcement points: 1) During sandbox
policy evaluation, entitlements relax specific restrictions defined in
sandbox profiles. 2) When accessing SIP/TCC-protected resources
or performing privileged operations, entitlements directly bypass
protection mechanisms. Our analysis shows entitlement-granted
capabilities depend on the kernel check’s context and location. Notably, entitlement names exhibit strong semantic correlations with
their functions and associated kernel enforcement paths.

7.3

macOS Security

Research on macOS security has explored several other directions,
including reverse-engineering of hardware features (e.g., prefetcher
security [14, 45] and system registers [41, 42], as well as security
feature bypasses [12, 22, 23]), cross-processor attack surfaces under
(e.g., GPU-based privilege escalations and jailbreaks [27, 31]), and
targeted fuzzing on both kernel modules and XPU firmware (e.g.,
KextFuzz [49], GraphicsFuzz [16], Crossfire [51]).

8

Conclusion

This paper identifies a previously overlooked attack surface in macOS PID-domain services operating within Application Sandboxes,
termed the Chekhov’s Gun attack. Through reverse engineering
of entitlement check policies applied to sandboxed services, we
designed a static detection tool based on taint analysis. Our automated framework discovered 19 zero-day vulnerabilities, highlighting critical risks in entitlement enforcement and underscoring the
need for stricter entitlement controls, even for PID-domain services
already confined by Application Sandboxes.
