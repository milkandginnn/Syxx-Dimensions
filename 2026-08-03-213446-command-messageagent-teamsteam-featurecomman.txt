  The reimagining thesis

  Mirror stops being a diluted echo of Prophet and becomes the Content-Integrity
  module, with Warp as its beating heart. Two features:

  Feature 1 — Kill the duplication (unify DNS consensus)

  Create one ResolverConsensusEngine (Kit-level cross-platform twin) that owns
  the single canonical resolver roster + fan-out and exposes both views from one
  query: symmetric peer consensus (Prophet's need) and asymmetric
  local-vs-consensus delta (Mirror's need). ProphetConsensus and VantageComparer
  both refactor to delegate to it — one roster, one tri-state, zero hand-sync.
  Mirror then sheds the full DNS resolver-matching column, keeping at most a
  one-line "DNS vantage" summary sourced from the shared engine (so content
  tampering is still situated against DNS tampering). Pure-DNS extras that were
  Mirror-only (DoH cross-transport, authoritative delegation) fold into
  Prophet/the shared engine. → the ~50% duplicate disappears.

  Feature 2 — Make Warp functional (the 5-step pipeline)

  1. Discovery (build): server-side domain component enumeration — extend the
  existing _AssetExtractor to also capture <img src/srcset>, <link 
  rel=preload/modulepreload/icon>, and CSS url() refs (fetch stylesheets,
  extract nested assets); optional bounded same-origin shallow crawl
  (config-capped, size-capped, reuses fetcher truncation). Output: a component 
  manifest (URL, type, same-origin vs third-party).
  2. Pull (extend): for each manifest entry fetch two copies — remote/clean via
  the off-path server proxy, local from the client's network — including binary
  bodies for images/fonts. Reuse SSRF-safe fetchers on both sides.
  3. Hash (extend + harden): SHA-256 every component body both sides (add
  CSS/image/font). Formalize a single canonicalization contract shared
  byte-for-byte across server + all clients, protected by cross-platform
  golden-vector tests (mirror the existing witness-crossplatform golden-vector
  pattern). Per-component status: match / mismatch / local-only / remote-only /
  fetch-failed.
  4. Render (extend + Linux parity): replace counts+badge with a component 
  integrity table (row per component → type, URL, honest tri-state pill) +
  headline "N of M deviate." Bring Linux to parity — it already shares the
  ContentWarp Kit; only VM+view wiring is missing (plus a license/DPAPI
  decision, ROADMAP G16).
  5. Side-by-side diff (build GUI): clicking a deviating component opens a diff
  pane — text components via TextDiff.unified(local, remote) (engine already
  exists, just never surfaced in GUI) in a monospace +/- colored scroll view;
  binary/image components show both + hash/byte mismatch. Retain per-component
  bodies on WarpResult, or fetch on demand via /api/warp/raw.

  Now #4 — fair question, I skipped the jargon.

  What a "canonicalizer" is: a function that rewrites content into one standard
  ("canonical") form before you hash it, so that meaningless formatting
  differences don't change the hash.

  Why Warp needs one: Warp's whole signal is "hash the local copy, hash the
  clean remote copy, compare." But the same HTML can be written slightly
  differently without any tampering — e.g. <img src="a" class="b"> vs <img 
  class="b" src="a"> (attribute order), extra whitespace, &amp; vs &, or CRLF vs
  LF line endings. If you hash those raw, the two hashes differ and Warp
  screams "tampered" when nothing was touched. A canonicalizer strips all that
  down to one form first — lowercase tags, attributes sorted, whitespace
  normalized, one line-ending style, UTF-8 — so identical content always 
  produces an identical hash.

  Why it's a decision, and where it bit us: that canonicalizer has to run in
  three places — the Python server, the Swift client, the C# client. If those
  three implementations disagree by even one byte (say, one uses a different
  whitespace rule), the local and remote hashes diverge and the user sees a fake
  "deviation" that's really just server-vs-client formatting, not network
  tampering. That's exactly the class of bug already live today (the
  trim/charset/modulepreload divergences). So #4 is:

  - Option A — one shared canonicalizer core: write the rulebook once (a small
  Rust/C library) and have Python, Swift, and C# all call that same compiled
  code. Identical by construction — it can't drift. More upfront plumbing
  (language bindings).
  - Option B — three hand-written copies + a shared test suite: each language
  implements the rules itself, and a golden-vector/fuzz test in CI checks they
  still agree. Less plumbing, but it's what exists now — and it has already
  drifted into the three live bugs, so it relies on discipline forever.

  My recommendation is A — the twins have already proven they drift, and Warp is
  a trust tool where a false alarm is fatal. But B is a legitimate "ship
  faster, guard with tests" choice. Which way do you want to call it?

  Sign the exact transmitted manifest bytes rather than a re-serialized         
  canonical form. Ed25519 signs the message bytes directly, so if you already   
  have one producer and one opaque manifest blob, detached signatures over the  
  transmitted bytes are the simplest and least divergent option.                
  [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8032)             
                                                                                
  ## Wire schema                                                                
                                                                                
  A practical manifest envelope is:                                             
                                                                                
  ```json                                                                       
  {                                                                             
    "version": 1,                                                               
    "timestamp": 1754253100,                                                    
    "origin_url": "https://example.com/login",                                  
    "html_sha256": "…",                                                         
    "assets": [                                                                 
      {                                                                         
        "url": "https://example.com/assets/app.js",                             
        "sha256": "…"                                                           
      }                                                                         
    ],                                                                          
    "redirect_policy": "follow-or-fail",                                        
    "freshness_seconds": 300,                                                   
    "signature_ed25519": "…"                                                    
  }                                                                             
  ```                                                                           
                                                                                
  The important part is that the client verifies the signature on the received  
  bytes first, then parses the manifest only after authenticity is established. 
  [swi-prolog](https://www.swi-prolog.org/pldoc/man?section=crypto-Ed25519)     
                                                                                
  ## Verdict rules                                                              
                                                                                
  The verdict lattice should be:                                                
                                                                                
  - `TAMPERING_DETECTED` if HTML bytes mismatch, the manifest signature fails,  
  or any fetched asset hash mismatches.                                         
  - `INCONCLUSIVE` if one or more listed assets cannot be fetched, but all      
  fetched assets match.                                                         
  - `VERIFIED_MATCH` only if every required byte is present and matches.        
  [html.spec.whatwg](https://html.spec.whatwg.org/multipage/parsing.html)       
                                                                                
  That keeps the fail-closed rule intact: missing data can reduce certainty,    
  but it cannot convert disagreement into success.                              
  [url.spec.whatwg](https://url.spec.whatwg.org/)                               
                                                                                
  ## Replay and freshness                                                       
                                                                                
  You were right to call out the replay hole. A signed manifest needs an        
  explicit freshness policy, such as a short validity window plus origin        
  binding, so an attacker cannot replay an old signed manifest and certify a    
  stale page state. A timestamp alone is not enough unless the verifier checks  
  it against an allowed age bound. [cryptobook.nakov](https://cryptobook.nakov. 
  com/digital-signatures/eddsa-and-ed25519)                                     
                                                                                
  If you want stronger replay resistance, include a nonce or session-bound      
  challenge in the witness exchange and sign that too. That gives the client a  
  way to reject a perfectly valid old manifest when freshness matters           
  operationally.                                                                
  [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8032)             
                                                                                
  ## Redirect and fetch policy                                                  
                                                                                
  Redirect behavior should be part of the protocol, because fetch and           
  navigation semantics differ, and redirect handling is not an incidental       
  detail. The Fetch Standard and HTML navigation algorithms treat redirects     
  through specific redirect-processing paths, so your verifier should either    
  require a declared redirect policy or fail closed on unexpected redirects.    
  [fetch.spec.whatwg](https://fetch.spec.whatwg.org/)                           
                                                                                
  A clean rule is:                                                              
                                                                                
  - For each manifest URL, either fetch the declared final URL exactly, or      
  require that redirects be explicitly listed and authenticated.                
  - If an unexpected redirect appears, classify it as `INCONCLUSIVE` or         
  `TAMPERING_DETECTED` depending on whether the target bytes are still part of  
  the authenticated set. [github](https://github.com/whatwg/html/issues/2396)   
                                                                                
  ## Asset closure                                                              
                                                                                
  The manifest should cover the full transitive asset closure, not just direct  
  references in the initial HTML. Otherwise `@import`, nested scripts, or       
  secondary fetches remain an uncovered tamper surface and become a source of   
  false confidence. [web-platform-tests](https://web-platform-tests.org/)       
                                                                                
  In practice, that means the server-side walker needs to include the same      
  resource types your integrity model cares about, and the manifest should      
  explicitly state what classes of assets are in scope.                         
  [web-platform-tests](https://web-platform-tests.org/)                         
                                                                                
  ## Reference validation                                                       
                                                                                
  Use `html5lib-tests` for HTML parsing conformance and `web-platform-tests`    
  for URL and fetch behavior. Those suites exist specifically to exercise       
  browser-aligned behavior across engines, which is what you want for the       
  reference derivation side. [firefox-source-docs.mozilla](https://firefox-sour 
  ce-docs.mozilla.org/web-platform/index.html)                                  
                                                                                
  That gives you a defensible validation matrix for the parser, URL resolver,   
  redirect policy, and asset-discovery logic before any manifest is signed.     
  [github](https://github.com/html5lib/html5lib-tests)                          
                                                                                
  ## Implementation rule                                                        
                                                                                
  The implementer-facing rule set is now:                                       
                                                                                
  1. Server fetches and parses.                                                 
  2. Server resolves the transitive closure.                                    
  3. Server emits an opaque signed manifest plus freshness metadata.            
  4. Client verifies signature on received bytes.                               
  5. Client fetches declared assets under the declared redirect policy.         
  6. Client hashes bytes and applies the verdict lattice.                       
  [fetch.spec.whatwg](https://fetch.spec.whatwg.org/)                           
                                                                                
  That preserves the original security goal while removing the need for JCS,    
  client-side parsing, and multiple canonicalization implementations.           
  [datatracker.ietf](https://datatracker.ietf.org/doc/html/rfc8785)
